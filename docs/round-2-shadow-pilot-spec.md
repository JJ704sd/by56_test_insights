# qualityctl Round 2 Spec：真实业务影子试点与有限硬门禁准入

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v0.1 |
| 状态 | 待评审 |
| 日期 | 2026-08-17 |
| 基线 | `origin/main@ddad399`，`qualityctl 0.1.0` |
| 阶段定位 | 真实业务影子试点，不阻塞生产发布 |
| 最短观测期 | 8 周，且至少覆盖 2 个完整迭代和 8 个合格变更 |
| 决策输出 | `GO_LIMITED_GATE / ADJUST_AND_REPEAT / STOP` |

## 1. 执行摘要

Round 1 已交付版本化输入 Schema、确定性规则核心、CLI、五个 MCP 工具、Windows
Python 3.11 CI 基线和仓库内 smoke test。当前产品定位是“可运行、可验证的软门禁”，
还没有真实业务数据证明它能在不增加高风险漏选和错误 `PASS` 的前提下节省人工时间。

Round 2 不直接建设企业生产硬门禁，也不继续扩展 Embedded UI。该阶段选择一个发布
频繁、目录较完整、风险可审计的真实模块，在现行人工流程旁路运行 `qualityctl`，冻结
每次输入与输出，独立比较人工结论和工具结论，并记录风险召回、错误放行、时间、维护
成本和净收益。工具结果只提供建议和证据，不自动改变测试范围或阻塞发布。

Round 2 完成后必须给出唯一阶段决策：

- `GO_LIMITED_GATE`：仅把稳定的输入完整性、Schema 和确定性高风险失败接入有限硬门禁；
- `ADJUST_AND_REPEAT`：安全指标合格，但样本、目录质量、流程或 ROI 尚不足，修正后重跑；
- `STOP`：发生错误 `PASS`、确认的高风险漏选、敏感数据事件或未经授权的自动放行。

## 2. 背景与当前基线

### 2.1 已具备能力

- `validate_change_risks`：校验八维风险清单；
- `select_regression_scope`：生成最小有效回归范围、排除理由和覆盖缺口；
- `evaluate_agent_evidence`：聚合冻结规格下的重复运行并拆分失败域；
- `assess_automation_roi`：计算自动化候选的净节省和回本周期；
- `decide_release_gate`：从原始证据重算最终 Gate，不接受调用方自填结论；
- Pydantic v2 与版本化 JSON Schema；
- CLI、stdio MCP、示例数据、单元测试和 Windows CI 基线；
- 只读 HTML/Embedded Inspector 尖峰，不具备审批或发布能力。

### 2.2 尚未证明的事项

- 一个真实项目能持续提供完整、版本化且无敏感信息的输入；
- 目录标签、组件映射和上下游映射足以避免高风险漏选；
- 工具结论与现行人工流程的差异可以被及时解释；
- 实际节省能够覆盖维护、误选、复核、runner 和数据维护成本；
- Agent 适用性、阈值和 ROI policy 来自可信、只读的审批来源；
- 企业环境中的认证、授权、审计、远程 MCP 和有限硬门禁可用性；
- Embedded UI 连续十次真实宿主稳定性及 3–5 人用户价值。

## 3. 目标与非目标

### 3.1 目标

1. 完成一个真实试点模块的接入清单、责任人、组件映射、测试目录和策略冻结。
2. 在影子模式下覆盖至少 8 周、2 个完整迭代和 8 个合格变更。
3. 对每个合格变更保留人工结论、工具结论、差异、裁决和最终结果。
4. 证明确认的高风险参考集没有漏选，且没有错误 `PASS`。
5. 量化风险盘点、回归筛选、Agent 证据整理和报告复核的人工时间变化。
6. 量化工具运行、维护、误报、flaky 调查、数据维护和残余人工复核成本。
7. 验证 Agent runner 无效、技术失败、确定性失败和语义失败能够分域记录。
8. 形成有限硬门禁的明确准入范围、回退条件和责任人，或作出调整/停止决定。

### 3.2 非目标

- 不自动批准阈值、风险接受、测试排除或发布结论；
- 不执行生产压测、安全扫描、故障注入、放量、回滚或生产数据写入；
- 不用 LLM Judge 独立裁决权限、计费、安全、数据写入和核心业务正确性；
- 不以扩大自动化率、减少用例数或增加 Agent 数量作为成功指标；
- 不建设新的测试管理平台、缺陷平台、Prompt 平台或远程审计服务；
- 不把 Embedded UI、Fullscreen、ChatGPT remote MCP 或视觉升级列为 Round 2 交付；
- 不在影子期让 `qualityctl` 退出码直接阻塞现有发布流水线。

## 4. 关键原则

1. **人工基线先冻结**：每次变更必须先冻结现行人工范围，再向评审者展示工具选集，
   防止工具结果反向污染基线。
2. **原始证据可追溯**：manifest、catalog、Agent spec/runs、工具报告和人工裁决均绑定
   稳定 ID、版本、时间和提交哈希。
3. **差异必须裁决**：人工与工具不同不自动代表任一方错误；由指定责任人在 SLA 内
   依据业务证据分类。
4. **安全指标优先**：任何错误 `PASS` 或确认的高风险漏选不能被平均节省时间抵消。
5. **缺证据不推定成功**：样本不足、输入漂移、审批来源不可信或 runner 无效时只能
   延长、调整或阻塞结论。
6. **不事后扩样挑结果**：冻结计划之外的运行单独记录，不得混入原计划分母。
7. **净收益核算完整**：维护、复核、误报、flaky、runner、LLM、数据和接入成本均计入。

## 5. 试点选择与启动门槛

### 5.1 试点模块选择条件

候选模块必须同时满足：

- 有明确的业务 owner、研发 owner 和测试 owner；
- 预计每周至少有一个可观测变更，能够在 8 周内积累不少于 8 个合格变更；
- 具有 30–50 条可维护的代表性测试目录，包含 smoke、核心链路和高风险标签；
- 组件、上游、下游和历史逃逸至少有一版可评审映射；
- 能在隔离测试环境运行，不需要 `qualityctl` 直接访问生产凭据或未脱敏数据；
- 现行人工流程有可记录的范围、结论和耗时；
- 业务 Oracle 可以说明，争议项有明确裁决人；
- 团队同意影子期工具不自动阻塞发布。

如果模块包含 Agent 能力，还必须具备冻结的 Agent、Prompt、模型、工具、知识库、
数据集、阈值档案和隔离 runner。若 Agent 确实不适用，必须提供批准的
`NOT_APPLICABLE` 依据，且最终报告不得宣称已验证 Agent 评测收益。

### 5.2 启动 Gate `R2-G0`

`R2-G0` 的工作包、依赖顺序、证据合同、验收场景和可拆票执行清单见
[R2-G0 Execution Spec](round-2-g0-execution-spec.md)。

以下项目全部完成后，8 周影子时钟才开始：

- 试点章程、范围、owner 和升级路径已批准；
- 测试目录包含 30–50 条唯一 ID，Schema 校验通过；
- 八维风险清单模板和组件/依赖映射已评审；
- Agent 适用性、阈值和 ROI policy 的来源与审批状态已冻结；
- 至少两个历史或前置迭代的人工基线可用；历史记录不完整时必须前瞻采集；
- 人工耗时采集方式通过一次演练；
- 影子 CI 或运行手册已演练，确认不会阻塞现有发布；
- 证据存储位置、访问权限、脱敏规则和保留周期已批准；
- 回退和紧急停止责任人明确。

## 6. 角色与职责

| 角色 | 主要职责 | 不得执行 |
| --- | --- | --- |
| 项目负责人 | 批准试点范围、ROI 门槛和阶段决策 | 单方面覆盖高风险失败 |
| 测试负责人 | 冻结人工基线、批准目录、主持差异裁决 | 事后修改人工基线而不留版本 |
| 测试工程师 | 维护 manifest/catalog、运行工具、记录耗时和证据 | 把工具选集描述为已执行或已通过 |
| 研发负责人 | 提供组件、依赖、修复点、自测和技术 Oracle | 将未知影响默认为不受影响 |
| Agent 负责人 | 冻结 Agent 指纹、维护 runner、解释技术失败 | 用重试覆盖首次有效失败 |
| 产品/业务裁决人 | 裁决业务语义、阈值和风险接受 | 修改原始运行证据 |
| 发布负责人 | 消费现有正式门禁、记录最终发布结果 | 在 Round 2 让影子 Gate 自动准出 |
| 安全/合规接口人 | 审核数据最小化、访问和保留策略 | 将敏感数据加入示例或普通日志 |

## 7. 试点数据与证据结构

建议在受控存储中使用以下逻辑结构；包含业务敏感信息时不得直接提交到本仓库：

```text
pilots/<pilot_id>/
├── charter.json
├── policies/
│   ├── agent-applicability.json
│   ├── threshold-profile.json
│   └── roi-policy.json
├── catalog/
│   └── test-catalog.json
├── baseline/
│   └── manual-effort.csv
├── changes/<change_id>/
│   ├── risk-manifest.json
│   ├── manual-scope.json
│   ├── selection.json
│   ├── agent-spec.json
│   ├── agent-runs.jsonl
│   ├── agent-report.json
│   ├── gate-report.json
│   └── adjudication.json
├── iterations/<iteration_id>/summary.json
└── final/round-2-report.md
```

### 7.1 合格变更定义

一个变更只有同时满足以下条件才进入主分母：

- 具有稳定 `change_id`、版本类型和变更提交/构建引用；
- 人工范围在查看工具结果前冻结并带时间戳；
- 八维 manifest、使用的 catalog 版本和工具版本可定位；
- 工具输出未经手工改写；
- 差异及最终裁决完整；
- 最终执行/发布结果可追溯；
- 不包含 Secret、未脱敏用户数据或生产写入指令。

不合格记录不得删除，必须进入排除清单并说明原因。若合格变更不足 8 个，延长试点，
不得复制、拆分或补造样本。

### 7.2 差异裁决分类

| 分类 | 含义 |
| --- | --- |
| `TOOL_TRUE_POSITIVE` | 工具发现人工基线遗漏的有效风险或用例 |
| `TOOL_FALSE_POSITIVE` | 工具多选/告警，经裁决确认无实际价值 |
| `TOOL_FALSE_NEGATIVE_HIGH` | 工具漏掉确认的高风险参考项 |
| `TOOL_FALSE_NEGATIVE_OTHER` | 工具漏掉确认的非高风险参考项 |
| `HUMAN_BASELINE_ERROR` | 人工基线自身不完整或不符合已批准规则 |
| `CATALOG_OR_MAPPING_DEFECT` | 目录标签、组件或依赖映射错误 |
| `POLICY_AMBIGUITY` | 阈值、适用性或业务规则未批准/不明确 |
| `RUNNER_OR_ENVIRONMENT` | runner、环境、采集器或依赖导致证据无效 |
| `NO_DIFFERENCE` | 人工与工具范围及状态一致 |

差异必须在 2 个工作日内完成初步分类；高风险差异必须在下一次发布前关闭或由授权人
明确阻塞。所有分类必须包含证据引用和裁决人。

## 8. 端到端运行流程

```mermaid
flowchart LR
    A["变更进入现行流程"] --> B["独立冻结人工风险与范围"]
    B --> C["冻结 manifest、catalog 与策略版本"]
    C --> D["旁路运行 qualityctl"]
    D --> E["保存风险、选集、Agent 与 Gate 报告"]
    E --> F["比较人工与工具结论"]
    F --> G["责任人裁决差异"]
    G --> H["按现行正式流程执行与发布"]
    H --> I["回填结果、耗时、逃逸与维护成本"]
    I --> J["迭代汇总与阶段决策"]
```

每个合格变更必须执行以下步骤：

1. 测试负责人按现行流程冻结人工风险、回归范围和预计耗时；
2. 研发负责人提供变更组件、上下游、修复点和自测引用；
3. 测试工程师冻结 manifest、catalog、policy 和工具版本；
4. 依次运行风险校验、回归选择、适用的 Agent 评测和最终 Gate；
5. 保存原始 JSON/JSONL 和标准输出，记录退出码、运行时间和提交哈希；
6. 解盲工具结果，生成差异清单；
7. 指定责任人完成裁决，不允许 LLM 投票替代责任人；
8. 仍按现行正式流程决定执行范围和发布；
9. 回填实际执行结果、缺陷、逃逸、人工耗时和工具维护耗时；
10. 每个迭代结束生成一次汇总，未关闭高风险差异不得进入下一阶段 Gate。

## 9. 指标与计算口径

### 9.1 安全指标（硬门槛）

| 指标 | 口径 | Round 2 门槛 |
| --- | --- | --- |
| 错误 `PASS` | 工具给出 `PASS`，但经裁决存在必需证据缺失、硬失败或未批准策略 | `0` |
| 确认的高风险漏选 | `TOOL_FALSE_NEGATIVE_HIGH` 数量 | `0` |
| 未经授权的自动放行 | 影子结论直接改变正式发布结论 | `0` |
| 敏感数据事件 | Secret、未脱敏数据进入输入、日志、报告或仓库 | `0` |
| 失败域可归因率 | 有效失败中可归入 runner/技术/确定性/语义域的比例 | `100%` |
| 重试证据保留率 | 发生重试时保留首次及所有后续尝试的比例 | `100%` |

“高风险召回”只能称为“对已确认参考集的观测召回”，不得宣称覆盖未知风险。参考集由
冻结人工范围、工具新增项、实际执行发现、逃逸缺陷和裁决结果的并集形成。

### 9.2 效率与质量指标

| 指标 | 计算方式 |
| --- | --- |
| 风险盘点时间变化 | `(基线中位分钟 - 影子中位分钟) / 基线中位分钟` |
| 回归筛选时间变化 | 同上，单独统计准备、复核和差异裁决时间 |
| Agent 报告整理时间变化 | 同上，仅适用于 Agent 域 |
| 有效覆盖缺口率 | 被裁决为有效的工具缺口数 / 工具报告缺口总数 |
| 工具误报率 | `TOOL_FALSE_POSITIVE / 工具新增项总数` |
| 目录缺陷率 | `CATALOG_OR_MAPPING_DEFECT / 合格变更数` |
| 证据完整率 | 证据包完整的合格变更数 / 全部合格变更数 |
| 运行可用率 | 无 runner/environment 无效的计划运行数 / 计划运行数 |

除安全硬门槛外，效率阈值必须在 `R2-G0` 前批准并写入 pilot charter。推荐初始目标为：

- 风险盘点、回归筛选和报告整理的合计人工中位时间下降不少于 20%；
- 证据完整率 100%；
- 工具误报造成的额外复核时间不超过节省时间的 30%；
- 所有差异均在 SLA 内分类，高风险差异 100% 关闭。

团队可以收紧推荐目标；任何放宽都必须有来源、批准人和版本，且不得放宽安全硬门槛。

### 9.3 ROI

```text
月人工毛节省 = 基线人工分钟 - 影子流程人工分钟
月工具总成本 = 维护 + 误报复核 + flaky 调查 + runner/环境 + LLM/运行 + 数据维护
月净节省 = 月人工毛节省 - 月工具总成本
预计回本月数 = 一次性接入与建设分钟 / 月净节省
```

进入 `GO_LIMITED_GATE` 至少要求：

- 试点最后两个连续迭代的净节省均为正；
- 8 周累计净节省为正；
- 持续维护和误选复核时间不超过已实现节省时间的 30%；
- 预计回本月数不超过 `R2-G0` 已批准的最长回本周期。

若月净节省不为正，则回本周期记为不可计算，不得用未来假设收益包装为通过。

## 10. 阶段 Gate 与时间线

| Gate | 时间 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| `R2-G0 READY` | 影子期前 | 第 5.2 节全部完成 | 批准启动 8 周时钟 |
| `R2-G1 HEALTHY` | 第 2 周 | 至少 2 个合格变更 | 无安全事件，证据链可用，差异流程运行正常 |
| `R2-G2 ITERATION_VALIDATED` | 首个完整迭代后 | 该迭代记录完整 | 高风险差异关闭，指标口径可复算 |
| `R2-G3 DECISION_READY` | 8 周且至少 2 个迭代、8 个变更后 | 样本和报告完整 | 作出唯一阶段决策并完成批准 |

历史数据只有在字段完整、时间可信、人工范围未受工具结果影响且可以复核时，才能用于
人工基线；否则必须前瞻采集至少两个迭代。准备期和基线采集期不计入 8 周影子时钟。

## 11. 决策规则

### 11.1 `GO_LIMITED_GATE`

必须同时满足：

- 全部安全硬门槛通过；
- 8 周、2 个完整迭代和 8 个合格变更均满足；
- 差异 100% 有裁决，高风险差异全部关闭；
- 效率与 ROI 达到已批准门槛；
- 团队能够持续维护 catalog、映射、策略和证据；
- 有明确的有限硬门禁范围、owner、监控、回退和停用开关；
- 安全/隐私/授权评审无未关闭的高严重度问题。

`GO_LIMITED_GATE` 只授权下一阶段设计以下硬规则：输入结构完整性、Schema、冻结指纹、
样本计划、runner 证据完整性和已批准的确定性高风险失败。业务语义、阈值争议、风险
接受、测试排除和生产发布动作继续人在环。

### 11.2 `ADJUST_AND_REPEAT`

适用于没有触发停止红线，但存在以下任一情况：

- 合格变更、迭代或观测期不足；
- catalog/映射缺陷率导致结论不稳定；
- 效率或 ROI 未达标但存在可验证的修正方案；
- Agent runner 或环境可用性不足；
- 策略来源和审批链尚未达到可信要求。

调整计划必须明确 owner、期限、要修改的单一变量和复验分母，不得只写“继续观察”。

### 11.3 `STOP`

发生以下任一事项立即停止扩面并回到纯人工/现有正式流程：

- 错误 `PASS`；
- 确认的高风险漏选；
- Secret 或未脱敏用户数据泄漏；
- 未经授权的豁免、范围修改或自动发布；
- 原始证据被覆盖、删除或无法审计；
- 连续两个完整迭代净收益不为正，且没有经批准的可验证修正方案。

## 12. Round 2 交付物

### 12.1 P0：启动前必须完成

- 修正 README、MVP Spec 和开发者指南中的过期状态与测试数量；
- 一份批准的 pilot charter 和 owner/RACI；
- 30–50 条真实、脱敏、版本化 test catalog；
- 组件/上下游映射和八维风险模板；
- 人工基线采集表与字段说明；
- Agent 适用性、阈值和 ROI policy 记录；
- 非阻塞影子运行手册或 CI workflow；
- 差异裁决模板和迭代汇总模板；
- 数据分级、访问控制、保留与删除方案。

### 12.2 P1：影子期完成

- 每个合格变更的完整证据包；
- 每个迭代的安全、效率、质量和 ROI 汇总；
- catalog/映射缺陷及修复记录；
- runner/环境无效记录和失败域统计；
- 8 周最终报告及可复算的原始指标；
- `GO_LIMITED_GATE / ADJUST_AND_REPEAT / STOP` 决策记录。

### 12.3 条件交付

- 只有试点确需 Agent 域时，才实现最小隔离 runner 适配器和人工复核回写；
- 只有作出 `GO_LIMITED_GATE` 后，才编写下一阶段认证、审计、可信策略源和有限硬门禁 Spec；
- Embedded UI 继续冻结；若单独恢复，必须使用独立 Spec 和预算。

## 13. 功能验收场景

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| R2-AC-001 | 人工范围尚未冻结就运行工具 | 该变更不得进入主分母 |
| R2-AC-002 | manifest 或 catalog 结构非法 | 保存 `BLOCKED` 证据，不静默跳过 |
| R2-AC-003 | 工具新增一个经裁决有效的高风险用例 | 记为 `TOOL_TRUE_POSITIVE` 并更新目录/映射 |
| R2-AC-004 | 人工参考集含高风险用例但工具未选 | 记为 `TOOL_FALSE_NEGATIVE_HIGH`，阶段决策 `STOP` |
| R2-AC-005 | 工具报告 `PASS`，但阈值来源未批准 | 认定错误 `PASS`，阶段决策 `STOP` |
| R2-AC-006 | Agent runner 无效 | 不计为产品失败，证据不足时 `BLOCKED` |
| R2-AC-007 | 重试后成功 | 保留首次失败和全部尝试，不重写分母 |
| R2-AC-008 | 8 周结束但只有 6 个合格变更 | 延长试点或 `ADJUST_AND_REPEAT`，不得宣称完成 |
| R2-AC-009 | 工具节省 100 分钟但维护/误报耗时 120 分钟 | 净节省为负，不得进入 `GO_LIMITED_GATE` |
| R2-AC-010 | 输入或报告包含 Secret | 立即停止，按安全流程处置 |
| R2-AC-011 | Agent 被批准为不适用 | Gate 使用可审计 `NOT_APPLICABLE`，报告不宣称 Agent 收益 |
| R2-AC-012 | 人工与工具无差异 | 仍记录耗时、版本和最终结果，记为 `NO_DIFFERENCE` |

## 14. 非功能要求

| 编号 | 要求 |
| --- | --- |
| R2-NFR-001 | 同一输入、策略和代码版本必须产生相同输出与 decision digest |
| R2-NFR-002 | 证据包必须包含生成时间、版本、变更 ID 和可定位的原始输入引用 |
| R2-NFR-003 | 影子运行不得延长或阻塞现有正式发布关键路径 |
| R2-NFR-004 | 业务敏感证据使用受控存储；仓库只保留脱敏 fixture 和模板 |
| R2-NFR-005 | 所有排除、修正和重跑均保留原记录，不覆盖历史 |
| R2-NFR-006 | 指标可由原始证据重复计算，不依赖手工修改的汇总数字 |
| R2-NFR-007 | 新增代码继续支持 Python 3.10+，并在 Python 3.11 CI 上验证 |
| R2-NFR-008 | 影子 workflow 使用只读或最小权限，不持有生产发布权限 |

## 15. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 人工基线被工具结果污染 | 无法比较真实差异 | 先冻结、后解盲；记录时间戳和版本 |
| 变更样本过少 | 指标不稳定 | 选择高频模块；不足 8 个则延长，不补造样本 |
| 目录和映射失真 | 漏选或误选 | 双人评审、缺陷分类、版本化修复和历史逃逸回流 |
| 团队只记录成功样本 | 选择偏差 | 建立 eligible change 台账，所有排除必须说明 |
| 工具耗时转移为维护耗时 | 虚假 ROI | 把维护、差异、runner 和数据成本全部计入 |
| LLM 解释被当成门禁结论 | 未授权放行 | 只认规则核心状态；报告标明权威字段 |
| 敏感数据进入证据 | 安全/合规事件 | 脱敏 fixture、受控存储、扫描与最小权限 |
| Embedded UI 分散试点资源 | 延误核心验证 | Round 2 明确冻结 UI 扩展 |

## 16. Definition of Done

Round 2 只有同时满足以下条件才算完成：

- `R2-G0` 的所有启动条件有批准记录；
- 完成至少 8 周、2 个完整迭代和 8 个合格变更；
- 每个合格变更均有人工基线、工具证据、差异裁决和最终结果；
- 全部指标可以从原始证据复算；
- 没有未关闭的高风险差异或安全事件；
- 维护、误报、runner、复核和数据成本均计入 ROI；
- 形成唯一的 `GO_LIMITED_GATE / ADJUST_AND_REPEAT / STOP` 决策；
- 决策由项目负责人、测试负责人和业务/产品裁决人签署；
- README、路线图和状态文档与最终事实一致；
- 若为 `GO_LIMITED_GATE`，下一阶段只描述准入范围，不在本阶段直接启用硬门禁。

## 17. 待评审决策

以下事项必须在 `R2-G0` 前填写，不得由工具自行推断：

1. 首个试点模块和 `pilot_id`；
2. 项目、测试、研发、Agent、业务和安全 owner；
3. 哪个系统是阈值、Agent 适用性和风险接受的权威来源；
4. 合格变更台账和证据包存放位置；
5. 已批准的最长回本周期；
6. 推荐效率指标是否收紧或在有依据时调整；
7. Agent 域是否适用，以及冻结 runner/数据集的方式；
8. 正式发布流程与影子 workflow 的隔离方式；
9. 数据分级、保留周期和删除责任人；
10. 发生停止红线时的通知和恢复流程。
