# 测试自动化机会地图与技能组演进建议

核验日期：2026-08-11

## 结论先行

现阶段不缺测试流程文档，也不缺“应该测什么”的原则；最值得投入的是把已经稳定的输入、判据、证据和门禁做成确定性组件。建议保持 `D:\quality_tests_skills` 现有 5 个质量技能的职责边界，不新增泛化的“测试自动化技能”，而是在现有技能下逐步增加 `scripts/` 与适配器。

第一优先级是两条闭环：

1. 变更事实 -> 八维风险清单 -> 最小有效回归选集 -> 自动化候选。
2. Agent 版本清单 -> 多次运行 -> 确定性断言 -> 人工语义复核 -> 统计与门禁。

本仓库已经交付两条闭环的最小可运行版本。它们自动化“整理、校验、计算、追踪”，保留“阈值批准、业务争议、产品验收、生产动作”给授权角色。

## 从规范中发现的四个关键矛盾

### 1. “全量执行”与“最小有效回归”并存

部分章节要求系统测试或大版本用例执行率 100%，另一些章节又要求按风险避免盲目全量。正确处理不是选一个口号，而是先版本化本次批准范围，再要求“批准范围内 100% 完成”。回归选择必须留下包含、排除、原因、剩余风险和重新纳入条件。

### 2. 自动重试可能制造虚假的稳定

工具规范要求失败重试，但 Agent 与稳定性规范又要求重试不能掩盖不稳定。本方案把 runner 无效、系统技术失败、确定性断言失败和语义失败分别统计；后续即使接入 pytest rerun，也必须保留首次失败和总尝试数。

### 3. 示例阈值存在口径冲突

物流数值示例同时出现绝对容差 `±0.01` 与相对误差 `<=0.01%`；基线退化 10% 也未统一说明百分点还是相对比例。组件要求显式选择绝对或相对容差，并同时报告百分点与相对变化。未批准时只能 `REVIEW_REQUIRED/BLOCKED`。

### 4. 3-5 次重复不等于充分统计把握

3-5 次适合作为每用例的最低执行量，却不足以单独证明一个高通过率。组件同时报告计划数、有效数、技术失败数、语义失败数和 Wilson 95% 区间。高风险场景仍执行“任一次有效失败即失败”，不允许被总体平均。

## 自动化价值判断

不要用“自动化覆盖率”单独驱动投入。每个候选至少回答：

| 维度 | 进入自动化的最低条件 | 不满足时 |
| --- | --- | --- |
| 频率 | 每月重复执行，或每次提交/发布必跑 | 保留手工或按风险触发 |
| 稳定性 | 行为、环境和数据可被固定 | 先改善可测性和隔离 |
| 可重复 | 能清理副作用并独立重跑 | 先补幂等、fixture 和恢复 |
| Oracle | exact、Schema、规则、状态或契约可判 | 语义争议保留人工复核 |
| 人工成本 | 执行时间 × 频率明显高于维护成本 | 不自动化或延后 |
| 风险价值 | 核心、高频、历史逃逸或影响面大 | 低风险一次性工作不优先 |
| 失败可诊断 | 有原始输出、Trace、日志和关联 ID | 先补可观测性 |

建议核心效率指标采用：每月净节省人工分钟、发现逃逸缺陷数、从变更到可信结论的时间、无效运行率、flaky 首次失败率、人工语义复核量和维护工时，而不是脚本数量。

| P2 | 确定性故障注入实验 | 超时、断连、坏 Schema、重试、副作用和恢复 | 仅隔离环境，先小范围代理级故障 | 条件采用 |

## 已实现组件

### 风险清单校验器

固定检查八个维度：

1. `business_flow`：用户/业务主流程与状态迁移。
2. `exception_paths`：失败、取消、超时、重试、降级。
3. `boundaries`：空值、极值、组合、长度、单位与临界点。
4. `permissions`：身份、租户、水平/垂直越权、工具权限。
5. `data_consistency`：跨表/服务/消息的一致性、对账和迁移。
6. `upstream_downstream`：契约、依赖失败、版本兼容与数据流。
7. `side_effects`：幂等、重复扣费/写入、通知、外部动作。
8. `recoverability`：回退、恢复、回切、清理和上下文延续。

`affected` 必须提供证据与可观察场景；`not_affected/not_applicable` 必须说明原因；`unknown` 必须有责任人和解决期限。这样把“补充测试思维”变成每次变更都要完成的契约，而不是一次培训口号。

### 回归选择器

选择器消费版本类型、变更组件、上下游、风险维度、风险信号和测试目录：

- 所有版本保留 smoke。
- 日常版本保留 CP0 core，并选变更、依赖、风险和历史逃逸相关用例。
- Hotfix 选择修复点、冒烟和最小影响面。
- 大版本选择完整目录，再由批准排除项约束。
- 每个选中用例输出理由；每个未覆盖的受影响维度输出缺口。
- 对未自动化用例计算“频率 × 人工分钟 - 月维护分钟”，但只有稳定、可重复、Oracle 清晰且净节省为正时才标为候选。

它不是代码级依赖分析器。组件映射和风险事实应由项目仓库提供，避免把文件名相似度误当成真实业务影响。

### Agent 评测聚合器

当前支持 `equals`、`number`（必须显式绝对或相对容差）、`required`、`one_of` 和 `matches` 断言；支持点路径访问嵌套字段。

运行状态分成：

- `runner_invalid`：采集器、脚本或环境失效，不进入有效分母并阻塞证据完整性。
- 技术失败：Agent/模型/工具超时、5xx 或系统错误，计入端到端失败。
- 确定性失败：字段、数值、格式、规则或状态不满足。
- 语义失败：人工复核明确失败。
- `REVIEW_REQUIRED`：语义复核缺失或非高风险阈值未批准。

高风险默认 `hard_fail_on_any=true`。组件保留逐次结果、分子/分母、Wilson 区间、基线百分点变化和相对退化，不用一句“总体通过率”隐藏失败。

## 热门开源项目的复用建议

选择开源项目的原则是“借能力，不复制平台”。本地组件负责统一风险、证据和门禁契约；具体执行器作为适配器接入。

| 能力 | 推荐项目 | 适合复用的部分 | 不建议的用法 |
| --- | --- | --- | --- |
| 稳定 Web 主链路 | [Microsoft Playwright](https://github.com/microsoft/playwright) | 多浏览器、隔离、自动等待、web-first 断言、Trace；CI 还支持 [only-changed](https://github.com/microsoft/playwright/blob/main/docs/src/ci.md) | 录制脚本不整理就入库；用 UI 替代接口/契约测试 |
| Python 性质测试 | [Hypothesis](https://github.com/HypothesisWorks/hypothesis) | 从输入域生成边界并缩小失败样本，适合计费规则、状态机和纯函数 | 用随机生成替代业务等价类和批准边界 |
| OpenAPI/GraphQL 边界与状态序列 | [Schemathesis](https://github.com/schemathesis/schemathesis) | 基于 Schema 生成边界、检查响应契约、串联状态化工作流，底层复用 Hypothesis | 对生产发起生成流量；把 2xx 当业务正确 |
| 消费者驱动契约 | [Pact](https://github.com/pact-foundation) | 消费者/提供者独立演进、Mock Server、Broker 和 CI 兼容门禁 | 单体项目或没有明确消费者时强行引入平台 |
| 设计优先 Mock/代理校验 | [Stoplight Prism](https://github.com/stoplightio/prism) | OpenAPI Mock、请求/响应验证代理、前后端并行 | 放在生产关键路径；把 Mock 行为当真实依赖质量 |
| 真实依赖集成测试 | [Testcontainers](https://github.com/testcontainers) | 临时数据库、消息队列等真实服务，减少共享环境污染 | CI 无容器能力或依赖启动成本过高时全量使用 |
| LLM/Agent CLI 评测与红队 | [Promptfoo](https://github.com/promptfoo/promptfoo) | 本地 CLI、模型/Prompt 对比、断言、CI 和红队适配 | 未冻结模型/Prompt/数据集就比较；用其单一分数准出高风险业务 |
| Agent/RAG 语义指标 | [DeepEval](https://github.com/confident-ai/deepeval) | pytest 风格集成、Agent 工具正确性、RAG、多轮和自定义指标 | LLM-as-a-judge 独占计费、权限、安全或核心规则判定 |
| Prompt/Trace/数据集证据层 | [Langfuse](https://github.com/langfuse/langfuse) | Prompt 版本、Trace、评测、数据集和人工标注 | 把平台中存在一条分数等同于可比较、已批准门禁 |
| 小范围网络故障 | [Shopify Toxiproxy](https://github.com/shopify/toxiproxy) | 在测试/CI 中确定性注入延迟、断连、限速和超时 | 跳过停止、清理和恢复验证；指向生产 |
| Kubernetes 混沌实验 | [Chaos Mesh](https://github.com/chaos-mesh/chaos-mesh) | 成熟 K8s 团队的故障编排和实验可视化 | 团队尚无隔离、观测、停止/恢复能力时过早引入 |

推荐采用顺序：

1. 已有 OpenAPI：先 Schemathesis；服务独立发布且消费者多时再加 Pact；设计期需要 Mock/代理时加 Prism。
2. Python 核心规则：先 Hypothesis；外部依赖使用 Testcontainers 提升真实性。
3. Web：只用 Playwright 覆盖登录、主链路和发布哨兵，优先接口/契约层。
4. Agent：先本地确定性评测契约，再选择 Promptfoo 或 DeepEval 作为执行适配器；Langfuse用于 Trace/Prompt/数据集证据。
5. 韧性：先 Toxiproxy 做可控依赖故障；只有 K8s 隔离与恢复体系成熟后再上 Chaos Mesh。

## Agent 类项目需要建立的不同评估意识

### 传统测试仍然保留

API 连通、Schema、计费公式、权限、幂等、数据写入、工具参数和副作用仍是确定性门禁。模型不能替代规则引擎或权威 Oracle。

### 评估单位从“一个输出”变成“一个版本化分布”

需要同时冻结：Agent、Prompt、模型与参数、规则、工具定义、知识库、Schema、数据集、runner、Judge、环境、采样和重试。任一绑定项变化，都可能使基线不可比较。

### Judge 是级联，不是单点

建议顺序：exact/Schema -> 确定性业务规则 -> 候选集合/量表 -> 人工复核。LLM Judge 可以辅助聚类、解释和低风险语义评分，但高风险场景必须有精确规则或人工证据。

### 失败需要分域

至少区分：runner 无效、系统技术失败、Schema/规则失败、工具规划失败、上下文失败、语义失败、安全失败和人工争议。重试后的成功不能删除第一次失败。

### 线上信号不是发布授权

线上采样用于漂移、用户反馈和问题发现；不能替代离线门禁，也不能自动执行停止或回滚。发布技能应消费 `OK/WATCH/STOP_RECOMMENDED` 与批准阈值，再由授权角色决定生产动作。

## 分阶段路线图

### 0-2 周：验证 P0 闭环

- 选择一个稳定 API/Agent 模块，用真实但脱敏的变更和 30-50 条测试目录试跑。
- 对照人工选集，记录漏选、误选、解释成本和净节省。
- 用一个 Agent 核心集跑 3-5 次，验证 runner/技术/确定性/语义分域。
- 只把 `risk-check` 作为软门禁；`select` 和 `agent-eval` 先输出 `REVIEW_REQUIRED`，由测试负责人确认。

退出条件：两次迭代没有高风险漏选；选择理由可被产品/研发/测试理解；运行证据可复现。

### 2-6 周：接入 CI 与开源适配器

- PR 阶段：风险清单校验 + 受影响测试选集；不完整则阻塞合并。
- 每日/版本：完整核心回归与 Agent 批量评测。
- OpenAPI 项目接入 Schemathesis；稳定 UI 主链路接入 Playwright Trace。
- 将失败样本自动回流为待评审测试数据，而不是直接污染核心基线。

退出条件：首次失败保留；flaky/runner 无效率可量化；人工回归时长下降且逃逸不升高。

### 6-12 周：证据门禁与韧性

- 实现证据包校验与测试准出门禁，消费范围、执行、缺陷、NFR 和 Agent 包。
- 以 Testcontainers/Toxiproxy 建立依赖失败、坏 Schema、超时、重试和恢复实验。
- 有独立消费者的服务按需引入 Pact；成熟 K8s 团队再评估 Chaos Mesh。
- 将 Langfuse 或现有 Trace 平台接为证据源，而不是新的唯一权威源。

退出条件：同一 build 的范围、版本、数据、环境、阈值和证据可一键追踪；缺证据不会被误判为通过。

## 明确不自动化的环节

- 尚未稳定或一次性的 UI/流程。
- 没有可观察 Oracle 的“看起来合理”。
- 产品对推荐、话术、体验和业务可接受性的最终裁决。
- 安全、权限、计费和合规的纯 LLM Judge 决策。
- 生产压测、安全扫描、破坏性故障注入。
- 未授权的发布、放量、停止、回滚和数据修复。
- 为提升“覆盖率”而复制相似输入、录制脚本或堆叠脆弱端到端用例。

这些不是“自动化能力不足”，而是判据、风险或授权边界决定的人在环位置。
